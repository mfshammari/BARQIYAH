# برقية — منصة إدارة دعوات المناسبات

منصة SaaS لإدارة دعوات الأعراس والمناسبات، موجّهة للسوق السعودي/الخليجي، وقناتها الأساسية واتساب.
ترقمن رحلة الدعوة كاملة:

> قائمة المدعوين ← إرسال الدعوة عبر واتساب ← تأكيد الحضور (RSVP) بأزرار تفاعلية ← باركود أحادي للمؤكِّدين ← تسجيل الدخول عند الباب بالمسح.

الموديل التجاري: **باقة لكل مناسبة** (لا اشتراك متكرر). الرصيد بالمقاعد يُستهلك عند الإرسال،
والتفعيل يدوي من الأدمن مبدئياً مع طبقة دفع مجرّدة جاهزة لـ Moyasar/Tap لاحقاً.

## التشغيل محلياً

```bash
npm install
cp .env.example .env.local     # ثم املأ مفاتيح Supabase
npm run dev                    # http://localhost:3000
```

المشروع **لا ينهار** عند غياب المفاتيح:

- بلا مفاتيح Supabase → تظهر شاشة «المنصة بحاجة إلى إعداد».
- بلا مفاتيح Meta → مزوّد واتساب يعمل بوضع **المحاكاة (Mock)**: الحالات والرصيد تتحدّث،
  والرسائل تُسجَّل في جدول `message_logs` دون إرسال فعلي. إضافة المفاتيح تحوّله للوضع الحقيقي تلقائياً.

### متغيّرات البيئة

```
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
META_PHONE_NUMBER_ID=
META_WABA_ID=
```

وإنشاء حسابات الماسحين. لا يُستورد في أي كود عميل.

## إعداد قاعدة البيانات

**الطريقة الأسرع** — ملف واحد: انسخ محتوى `supabase/setup.sql` كاملاً والصقه في
Supabase Studio ← **SQL Editor** ← New query ← Run. الملف مولّد آلياً من ملفات الترحيل
وآمن لإعادة التشغيل.

أو شغّل ملفات `supabase/migrations` بالترتيب إن كنت تفضّل التتبّع خطوة بخطوة:

1. `0001_init.sql` — الجداول والأنواع والفهارس وتريغر إنشاء الملف الشخصي.
2. `0002_rls.sql` — تفعيل RLS على **كل** جدول مع سياساته.
3. `0003_functions.sql` — دوال الرصيد والحجز والـ RSVP والمسح والتفعيل.
4. `0004_profile_safety.sql` — منع ترقية الصلاحيات وشبكة أمان الملف الشخصي.

> عند تعديل أي ملف ترحيل، أعد توليد الملف المجمّع وافحصه: `npm run check:sql`

> **تحذير من فخ حقيقي:** محرر SQL في Supabase ينفّذ الملف الملصوق **كمعاملة واحدة**،
> وPostgres يمنع استخدام قيمة enum أُضيفت في نفس المعاملة (`55P04`). لذلك تُقارَن
> الأدوار وما شابهها **كنص** (`role::text = '…'`) لا كقيم enum. يفحص ذلك آلياً
> `scripts/check-setup-single-tx.mjs` ويعمل ضمن `npm test`.

### إنشاء أول أدمن

بعد تشغيل المخطط، أنشئ مستخدماً من **Authentication ← Add user** (فعّل Auto Confirm)،
ثم اجعله أدمن من SQL Editor:

```sql
update public.profiles p set role = 'admin'
from auth.users u
where u.id = p.id and u.email = 'بريدك@هنا';
```

الدور لا يمكن تغييره من التطبيق نفسه: تريغر `profiles_guard_role` يمنع أي مستخدم من
ترقية دوره، فالترقية تتم من SQL Editor أو من حساب أدمن قائم.

ثم البيانات التجريبية (اختياري):

```bash
node scripts/seed-users.mjs          # ينشئ الأدمن وصاحب المناسبة والماسح
# ثم شغّل supabase/seed.sql في SQL Editor
```

حسابات التجربة (كلمة المرور `Barqiyah#2026`):

| البريد | الدور |
|---|---|
| `admin@barqiyah.sa` | سوبر أدمن |
| `owner@barqiyah.sa` | صاحب مناسبة |
| `scanner@barqiyah.sa` | ماسح |

كلا الملفين (`seed-users.mjs` و `seed.sql`) قابلان لإعادة التشغيل دون تكرار البيانات.

## منطق الرصيد (جوهر النظام)

الرصيد يُحسب **بالمقاعد (الأشخاص)** لا بعدد الدعوات، وله ثلاث حالات:

| الحالة | التعريف |
|---|---|
| **مؤكّد** | مجموع `confirmed_seats` للمدعوين بحالة `accepted` أو `attended` |
| **محجوز** | مجموع `max_seats` للمدعوين بحالة `sent` — نحجز الحد الأقصى حتى يصل الرد |
| **متاح** | `seats_quota − محجوز − مؤكّد` |

القواعد المطبَّقة:

1. الدعوة تعرض حداً أقصى (مثال ٧)، والمدعو يؤكّد عدداً فعلياً ≤ الحد الأقصى (مثال ٣) — والفرق يُحرَّر فوراً.
2. **الرسائل منفصلة عن المقاعد**: كل مدعو = رسالة واتساب مدفوعة واحدة مهما كان عدد مقاعده.
3. الإرسال يُمنع عند نقص الرصيد، مع تنبيه بعدد المقاعد الناقصة بالضبط.
4. الحجوزات المعلّقة تظهر بوضوح في اللوحة، وتُحرَّر عند الاعتذار.
5. اللوحة تفصل رقمين: **الرسائل المستخدمة** و**إجمالي الحضور المتوقع (مقاعد)**.
6. عدد مقاعد الدعوة = عدد مرات مسح الباركود المسموحة.

الحجز يتم داخل دالة `reserve_seats_for_send` التي **تقفل صف المناسبة** (`select … for update`)،
فلا يتجاوز الرصيدَ إرسالان متزامنان. عند فشل الإرسال عبر واتساب يُحرَّر الحجز تلقائياً
(`release_seat_hold`) حتى لا يُستهلك رصيد على رسالة لم تصل.

## الأدوار والصلاحيات

| الدور | نقطة الدخول | الصلاحيات |
|---|---|---|
| **سوبر أدمن** | `/admin` | كل المناسبات والعملاء، الباقات، مكتبة القوالب، طلبات القوالب، التفعيل اليدوي، إعدادات Meta |
| **صاحب المناسبة** | `/events` | مناسباته فقط: المدعوون، الدعاة، القالب، حسابات المسح، الرصيد والترقية |
| **الماسح** | `/scan` | شاشة المسح فقط لمناسبته — لا يرى لوحة المناسبة |
| **المدعو** | `/rsvp/[token]` | بلا حساب: تأكيد/اعتذار وتحديد العدد، ثم `/i/[qr_token]` لعرض الباركود |

العزل مضمون بـ RLS على مستوى قاعدة البيانات (وليس في كود الواجهة فقط):
لا يوجد أي جدول بلا RLS، ولا توجد أي سياسة تسمح للزائر (`anon`) بقراءة أي صف.
صفحات المدعو العامة تمرّ عبر `service role` على الخادم بعد التحقق من التوكن.

**ترقية الصلاحيات مسدودة**: RLS لا تستطيع تقييد عمود بعينه، فلولا حماية إضافية لأمكن
لأي مستخدم مسجّل تنفيذ `update profiles set role = 'admin'` على صفّه ويصير أدمن.
تريغر `profiles_guard_role` يرفض أي تغيير للدور ما لم يكن المنفّذ أدمن أو كود خادم موثوق.

## تكامل واتساب

### المتطلبات لدى Meta

1. حساب WhatsApp Business (WABA) + توثيق النشاط التجاري (Business Verification).
2. **System User** بتوكن دائم يحمل صلاحية `whatsapp_business_messaging`.
3. اعتماد الاسم المعروض (Display Name) للرقم.
4. قوالب معتمدة، وربط كل قالب باسمه في Meta من `/admin/templates`.

### ربط الـ Webhook

- الرابط: `https://<domain>/api/whatsapp/webhook`
- التوكن: قيمة `META_WEBHOOK_VERIFY_TOKEN` (أو المحفوظة في `/admin/integration`)
- الاشتراك في حقل `messages`

### مسار الرد

| فعل المدعو | ما يحدث |
|---|---|
| ضغط «تأكيد» ودعوته بمقعد واحد | تأكيد فوري + إرسال الباركود |
| ضغط «تأكيد» ودعوته بأكثر من مقعد | تصله قائمة تفاعلية لاختيار العدد الفعلي (حتى ١٠)، وما فوقها رابط صفحة الرد |
| اختيار العدد من القائمة | تأكيد بالعدد المختار + إرسال الباركود |
| ضغط «اعتذار» | تحديث الحالة وتحرير المقاعد المحجوزة |
| رسالة حرّة | تُصنَّف تلقائياً (تأكيد/اعتذار) مع تطبيع الهمزات، وإلا تُسجَّل فقط |

الباركود يُرسل كرسالة صورة حرّة داخل نافذة الخدمة (٢٤ ساعة) التي فتحها رد المدعو للتو.

## فحص الإعداد بعد النشر

```
GET /api/health
```

يجيب على سؤال واحد: هل التطبيق موصول بقاعدة البيانات فعلاً؟ لا يكتفي بوجود المفاتيح،
بل ينفّذ استعلاماً حقيقياً على القاعدة. لا يكشف أي قيمة سرّية — حالات منطقية فقط.

```json
{
  "ok": true,
  "database": { "connected": true, "schema_ready": true },
  "config": { "NEXT_PUBLIC_SUPABASE_URL": true, "...": true },
  "whatsapp": "mock"
}
```

| `database.reason` | المعنى |
|---|---|
| `MISSING_KEYS` | مفاتيح Supabase غير مضبوطة في البيئة |
| `UNREACHABLE` | المفاتيح موجودة لكن تعذّر الوصول للمشروع (رابط خاطئ أو مشروع متوقف) |
| `SCHEMA_MISSING` | الاتصال ناجح لكن الجداول غير موجودة — شغّل `supabase/setup.sql` |
| `42501` | الاتصال ناجح لكن الصلاحيات ناقصة على الجداول |

يرجع `503` ما لم يكن كل شيء جاهزاً، فيصلح كنقطة فحص آلية.

## الدفع

المرحلة الحالية: **تفعيل يدوي** من `/admin/events` — يضبط `events.status = active`،
يضيف رصيد المقاعد، ويسجّل العملية في `transactions`.
صاحب المناسبة يطلب الترقية من `/e/[id]/info` فتُسجَّل عملية معلّقة تنفّذها الإدارة.

الكود مهيّأ بطبقة `PaymentProvider` مجرّدة في `src/lib/payments` — إضافة Moyasar أو Tap
تعني مزوّداً جديداً يطبّق نفس الواجهة، دون إعادة هيكلة.

## نقاط مفتوحة تحتاج قراراً

1. **موافقة المدعوين المسبقة** على استقبال رسائل واتساب — تؤثر مباشرة على تقييم جودة الرقم الواحد
   لدى Meta. حالياً لا يوجد تحقق من الموافقة؛ يُنصح بإضافة إقرار على صاحب المناسبة عند الرفع.
2. **الحجم الشهري المتوقع للمناسبات** — يحدد الحاجة لطابور إرسال (queue) بدل الإرسال المتسلسل
   الحالي في الموسم.
3. **متابعة الباركود**: رسالة حرّة داخل نافذة الـ٢٤ ساعة (المطبَّق حالياً) أم قالب مدفوع منفصل؟
